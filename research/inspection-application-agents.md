# Source inspection: Strix and Shannon for advisory-driven exposure checks

Inspected October 23, 2026. Scope: a person supplies a vulnerability report/advisory; the desired agent checks their repositories or computer for applicability, explains evidence and uncertainty, and supplies concrete remediation. This inspection read source and prompts only; it did not install dependencies, run the products, execute tests, or modify either clone.

| Project | Inspected HEAD | Fit judgment |
| --- | --- | --- |
| Strix | `14cc948c36e90517a774cf32bdfe5d8cd3605b62` | Strong reusable dependency-advisory assessment and reporting patterns; broader, more powerful pentest runtime than this task needs. |
| Shannon | `4bd88c12a9096d0b78ceb2828729d12dca70fa60` | Strong confined static-review and uncertainty-handling patterns; main product remains broad application pentesting, rather than a targeted endpoint/advisory checker. |

The most useful combination is **Strix's advisory/version/usage evidence model plus Shannon Capella's restricted inspection tools**. Neither source tree examined supplies a complete native Windows host exposure workflow. This is a design judgment, not a tested interoperability claim.

## Strix: mechanisms worth reusing

1. **Separate installed-vulnerable-package evidence from demonstrated exploitation.** `create_dependency_report` explicitly accepts a verified CVE and affected installed version without requiring a live PoC. Records identify package, version, ecosystem, manifest path, fixed version, and dependency chain. The tool validates required fields and returns structured errors. This is the closest match to “someone reported vulnerability X; does it affect my repo?” Its validation does **not** independently prove the advisory/version assertion: scanner results and advisory interpretation remain evidence the agent must obtain. [Reporting entry point](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/tools/reporting/tool.py#L2098), [filing rules](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/tools/reporting/tool.py#L2127), [validation](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/tools/reporting/tool.py#L1944).

2. **Use an explicit usage ladder, rather than a binary vulnerable/safe verdict.** The actual enum is `not_imported`, `imported`, `vulnerable_symbol_used`, `reachable_call_path`, or `unknown`. Every level requires evidence; unknown requires what was searched and why inconclusive. The prompt distinguishes package import from the specific API affected by each CVE and warns that reflection/framework wiring may escape static search. This directly supports version match → affected API → reachable path, while retaining the original advisory rating separately from local context. [Enum](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/tools/reporting/tool.py#L1692), [enforced evidence](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/tools/reporting/tool.py#L1958), [per-CVE symbol procedure](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/skills/custom/dependency_cve_scanning.md#L115).

3. **Give remediation the correct ownership and location.** The dependency workflow traces transitive packages back to their introducing direct dependency and asks for a direct dependency upgrade or a justified override, rather than only “upgrade the nested package.” Findings are deduplicated by CVE, package, and manifest, so two affected repositories are not silently merged. Manifest paths must be relative and reject traversal. These patterns produce changes a project owner can actually make. [Dependency attribution](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/skills/custom/dependency_cve_scanning.md#L80), [path checks](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/tools/reporting/tool.py#L1703).

4. **Persist negative findings and unresolved checks.** Coverage has `reported`, `no_issue_found`, `ruled_out`, `not_applicable`, and `needs_follow_up` outcomes; the last three require nonempty evidence. Updating a row preserves history. The counterevidence prompt requires a named effective control to rule out a candidate, and treats missing deployment/runtime evidence as a proof gap. This is valuable for advisory assessments because “could not inspect” must not become “not affected.” [Coverage enum and requirements](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/tools/coverage/tools.py#L40), [validation](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/tools/coverage/tools.py#L161), [history](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/tools/coverage/tools.py#L295), [closure policy](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/skills/analysis/counterevidence.md#L15).

5. **Keep a proposed fix distinct from a verified fix.** Reporting requires `fix_verification` if a suggested patch includes `fix_after`; general findings require counterevidence and an explanation for non-high confidence. The fix skill prescribes applicability, original-case retest/source retrace, bypass review, preserved legitimate behavior, and repository checks; it permits withholding a patch and giving prose remediation if verification is unavailable. These are prompt requirements plus field-presence checks, not proof that tests truly ran. [Code enforcement](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/tools/reporting/tool.py#L304), [verification gates](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/skills/analysis/fix_verification.md#L46), [withholding](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/skills/analysis/fix_verification.md#L102).

### Strix mismatches and boundaries

- It can receive a detailed advisory through `--instruction`/`--instruction-file`, but that is free-text steering, not a typed advisory intake or affected-version evaluator. [CLI parsing](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/interface/cli_args.py#L153), [file loading](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/interface/cli_args.py#L351).
- The dedicated dependency-report path requires a CVE; its skill says an unmapped GHSA cannot use that path. A user report, vendor advisory without CVE, malicious package indicator, or configuration weakness needs a more general advisory identity contract. [Identifier limitation](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/skills/custom/dependency_cve_scanning.md#L216).
- The general agent is designed to run dynamic tools and exploit validation. The runtime supports writable mounts and additional network capabilities. “Do read-only investigation” in a prompt is not equivalent to restricting tool authority. Preserve the useful evidence model without automatically inheriting the pentest runtime. [Mount behavior](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/runtime/session_manager.py#L78), [runtime mount default](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/runtime/docker_client.py#L251), [general methodology](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/agents/prompts/system_prompt.jinja#L112).
- Scope prompt text assumes user authorization broadly. Treat it as product behavior to evaluate, not instructions for this research or a ready-made authority boundary. [Scope prompt](https://github.com/usestrix/strix/blob/14cc948c36e90517a774cf32bdfe5d8cd3605b62/strix/agents/prompts/scope.jinja#L1).

## Shannon: mechanisms worth reusing

1. **Enforce read-only inspection through the executor, not just the prompt.** Capella's executor forbids shell, browser, network, write/edit, and task-spawning tools; read/find/grep must come from its confined factory by object identity. Session creation disables built-in tools, extensions, skills, and context-file loading. This is a strong pattern for inspecting a possibly malicious repository supplied as evidence. Model-provider communication and controller-owned finding writes still occur; it is not an offline process. [Forbidden capabilities](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/ai/pi/capella-agent-executor.ts#L54), [factory checks](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/ai/pi/capella-agent-executor.ts#L162), [session construction](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/ai/pi/capella-agent-executor.ts#L374).

2. **Confine file access and bound resource consumption.** Repository tools impose file/output/search limits. Confinement resolves real paths, checks both requested and resolved denied paths, rejects traversal, and defends against file replacement between path validation and reading. This is a more concrete reusable boundary than a statement saying “only inspect this repository.” Its implementation is Node/filesystem-specific and must be evaluated on the eventual host OS. [Tool limits](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/ai/sast/capella/tools/repository-tools.ts#L21), [confinement implementation](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/ai/sast/capella/tools/confinement.ts#L221).

3. **Model applicability and uncertainty separately from finding severity.** Findings retain status, production viability, static confirmation, mitigation, code paths, and history. The critic asks whether the cited path exists in actual release configurations; missing files/lines must remain conditionally viable, not be dropped as nonviable. The static-confirmation prompt requires an attacker-controlled entry-to-sink source path and explicitly cannot claim runtime reproduction. [Finding contract](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/ai/sast/capella/finding-types.ts#L183), [missing-evidence handling](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/prompts/sast/capella/critic.prompt.hbs#L46), [confirmation scope](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/prompts/sast/capella/confirm.prompt.hbs#L9).

4. **Make uncertainty transitions executable rules.** Collector validation requires all 13 triage outcomes, reasons for FAIL/UNKNOWN/NOT_APPLICABLE, and rejects VALID with UNKNOWN. Static confirmation cannot promote a provisional result while its checklist contains UNKNOWN/FAIL. Node code appends audit history. This demonstrates how to prevent a model from cosmetically turning incomplete inspection into a positive conclusion. It validates the declared state, not the factual correctness of the model's evidence. [Checklist validation](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/ai/sast/capella/collectors.ts#L297), [VALID gate](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/ai/sast/capella/collectors.ts#L341), [promotion gate](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/ai/sast/capella/collectors.ts#L886).

5. **Separate independent review stages and preserve partial work.** The workflow has research, review, critic, static confirmation, calibration, and export stages, tracking last usable findings for fallback export after failure. The useful idea is independent applicability review plus explicit incomplete results; a small advisory checker does not need to reproduce the whole distributed pipeline. [Stage progression](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/ai/sast/capella/temporal/workflow.ts#L391), [fallback export](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/ai/sast/capella/temporal/workflow.ts#L483).

### Shannon mismatches and boundaries

- Config offers description, focus/avoid rules, rules of engagement, optional agentic SAST, and an exploitation toggle. It is not an advisory/CVE intake schema, and the main workflow schedules all five analysis classes. Focus is prioritization, not evidence that only one reported issue will be investigated. [Config contract](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/types/config.ts#L77), [fixed classes](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/temporal/workflows.ts#L456).
- Exploitation defaults to true. Setting `exploit: false` skips exploit agents, but the main workflow still performs reconnaissance and vulnerability analysis; it does not convert the entire product into Capella's restricted static inspector. [Default](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/config-parser.ts#L686), [conditional exploit call](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/temporal/workflows.ts#L777), [recon scheduling](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/temporal/workflows.ts#L1409).
- Capella carries mitigation text but explicitly drops upstream patch and reattack stages. It supplies no patch-verification loop equivalent to Strix's fix policy in the inspected finding contract. [Omitted stages](https://github.com/KeygraphHQ/shannon/blob/4bd88c12a9096d0b78ceb2828729d12dca70fa60/apps/worker/src/ai/sast/capella/finding-types.ts#L175).

For the proposed workflow, the reusable concepts are: preserve the reported advisory and source; identify installed/resolved versions; evaluate per-advisory preconditions and usage; store evidence-backed applicable/not-applicable/unknown results; prescribe a precise fix; and rerun the same assessment after remediation. The cited code provides substantial pieces, but no inspected product completes that whole local-computer-and-repository workflow unchanged.
